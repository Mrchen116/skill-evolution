## A. 总体框架决策

### A1 · F4·B 的定位 = 跨会话统计挖掘层
B 是三套自动机制里**唯一做"跨会话统计挖掘"的那层**：把同一个 skill 的**许多次已结束会话**汇起来，找**反复出现的系统性缺陷**（≥2），而非一次性噪声。
- **为什么**：A（实时单 session）结构上给不出"反复"（support_count 永远=1）；C（Curator）只读 skill 文档做维护、不读轨迹挖新缺口。**A 太近视、C 是管家，B 卡在中间挖共性。**
- 用户确认了这个定位（"对"）。

### A2 · 两条实现路线范式：Workflow vs Agent
四个参考分属两种范式，这是比"搬哪个零件"更上位的轴：
- **Workflow（管线）**：把活拆成显式阶段，**代码当指挥**，多个窄 LLM 调用（SkillOpt / Trace2Skill map-reduce）。
- **Agent（一步到位）**：**一个子 agent + 一段主 prompt + 工具**，agent 自己一个回合干完（auto-dream / Codex）。
- 用户原话："ABC…这是agent模式，一步到位。"

### A3 · 出两套方案（W 和 A），一套套讨论
- 用户原话："我们可以设计两套方案，分别是workflow和agent的。然后我们再一套套讨论。"

### A4 · 参考分析方法：每个来源写清"可参考/不可参考"，四类速查
每个 research 文档末尾按四类拆：① **纪律/内容**（进 prompt，W/A 都用）② **工作流编排件**（只 W 显式用，A 被 agent 回合吸收）③ **不能学**（离线特权）④ **似是而非**（旧误判更正）。表格分四列：**名字 | 是什么 | 为什么(不)能学 | 怎么用·出处**。
- **为什么**：先把素材按"进 prompt / 只 W 用 / 不能用"分好，出方案时融合不必再想。
- 已落地：01、03、05、07 均补了该速查。

### A5 · 决策 E（核心）：在线不做"效果反馈"，对齐 Hermes
A/B/C 都是**在线进化**（用户日常用着就在进化），区别于 SkillOpt/Trace2Skill 的离线进化。**Hermes 是最成熟的在线方案，它刻意不衡量"改动有没有效"**（一手确认：usage 只记 `use/view/patch_count` 零成败信号、Curator 只按时间衰减、A 改完不回头看）。**它不做，我们也不做。**
- **删除**：效果打分、失败指纹跨批比对、复发回滚、outcome-driven rejected_edits、"步6 自纠"。
- **在线质量改靠四样**：① 入口证据门槛（跨会话反复 ≥2 才改）② 可逆（每改快照 + archive 不硬删 + provenance 护 seed/user）③ 持续进化自然收敛（真实需求反复产证据，下轮继续朝它改）④ C 周期维护。
- **为什么**："改完有没有用"的反馈，四个参考没一个能在线给（SkillOpt 靠 gate 重跑、Trace2Skill 靠 gold 重测，都离线；Hermes/auto-dream/Codex 根本不做）。我那条"指纹比对自纠"是把离线 gate 山寨到在线——成熟在线方案不走这条。
- 用户原话："Hermes作为最成熟的在线skill自进化的方案，他不做这个设计，我们也不做这个设计。"
- **残余风险（接受）**：判错的坏改动若之后不再被新证据触发，会一直留着（没人主动测/回退）。缓解 = 改动有界（危害小）+ ≥2 闸（少出坏改动）+ C 维护 + provenance（留将来部门级复查）。这是成熟在线方案都接受的代价。

### A6 · ≥2：原则普遍存在，但取 Codex 的"硬门槛"形态
"反复=信号"在三个参考都有，但形态不同：
- **Codex**：显式硬门槛"**至少发生过两次**"——唯一一个硬的。
- **SkillOpt**：定性"找共性、非单次边缘" + support_count（一个数，但 `clip.py` 排序时**不卡 ≥2**）——软。
- **Trace2Skill**：分池 + 合并去重涌现（甚至单任务就产教训，不要求 ≥2）——更软。
- **为什么取硬形态**：SkillOpt/Trace2Skill 敢做软，是**因为后面有离线安全网兜底**（gate 重跑 / gold 重测）。我们在 E 之后**抽掉了后端**，≥2 要**独自承担**原本两道防线分担的重量 → 必须取最强的硬形态（Codex），软的会漏。

### A7 · ≥2 是"逼扎实的 LLM 判断"，不做代码核验；W/A 是纯工程权衡
- 要求 LLM 输出"≥2 + 证据引用（指出哪几段会话 + 每段证据）"，**目的是逼它按这个方式思考、把判断做扎实**，**不是给代码核验**——"这几段算不算同一个反复问题"是语义判断，**代码核验不了那个真正要紧的，所以不验证**。
- 用户原话："让他输出是让他强制按这个去思考而已。你真正没法验证。不用验证。"
- **连带更正**：我之前"≥2 必须可代码核验 → 收敛到丙"的推导**作废**。≥2 在 W 和 A 里都是同一种 LLM 判断、同一种加固（强制带证据），**没有谁更硬**。**代码只管结构安全**（快照/格式校验/conflict/写坏处理）。于是 **W vs A 退化为纯工程权衡**（可控成本 vs 顺 CC 纹理/MCP 内联），**不是"质量靠谁更稳"**。

### A8 · ≥2+证据 的落点
- **Agent 方案**：写在那**一个主 prompt** 里。
- **Workflow 方案**：写在**第一个看到多条轨迹的节点**的 prompt 上（SkillOpt 的桶内 analyst / Trace2Skill 的 merge）。**绝不在打标器（一次只看一段，无从判断反复）。**
- 我们小批量 W：让 analyst 一次看整桶、当场出 support_count + 证据，merge 常跳过。

## B. Agent 方案专项决策

### B1 · 怎么改 + 备份：直接抄 Hermes（`skill_manage` 工具 + `curator_backup` 快照）
一手确认 Hermes 的做法，比我之前给的"裸 Edit + 事后格式 VERIFY + 单独 rollback"更好，照搬：
- **怎么改 = 给 agent 一个 `skill_manage` 式工具**（`skill_manager_tool.py`），**不是裸 `Edit`/`Write`、也不是"产补丁给代码 apply"**。4 个 op：
  - `create`（新建）/ `edit`（整写 SKILL.md）/ `patch`（任意文件定向 find-replace，**不匹配时回 preview 让模型自修**——B1 原本的"自修"是这个工具自带的）/ `write_file`（增/覆盖支撑文件）。
  - 工具内置：frontmatter/大小/名字校验、路径白名单（只能写 skill 目录的允许子目录）、原子写、pinned 保护。
  - → agent 仍自己驱动（agent 模式），但**改动走一个受约束、自带校验的工具**，校验在每次调用里就做。
- **备份 = `curator_backup.py` 式快照**：动手前对 skill 树打 tar.gz 快照（+ manifest 记原因/时间）；回滚时连"把当前树挪走"也存成快照（**回滚本身可撤销**）。**这就是决策 E"可逆"那条的现成实现。**
- 收回我之前的"裸 Edit/Write + 事后格式 VERIFY + rollback"那套。

### B2 · 不开窗：覆盖完整 session，不在 skill 调用处切片
- **为什么**：判成败的关键信号——**用户纠偏往往在 skill 出结果之后、任务成败在 episode 末尾**；在调用处开窗正好把这些切掉。
- **依据**：所有做使用分析的方法（SkillOpt 读整个 conversation.json、Trace2Skill 读整个任务 log、Hermes 看整段会话）**单位都是"完整 episode"，没有一个开窗切片**。
- 用户原话（要我核对各方法怎么读）："你看到有任何一个方法这样做吗，所有这些分析轨迹的方法，分别是如何读轨迹的？"

### B3 · 不 inline 全文：用 Codex/auto-dream 式"文件+只读工具+逐段蒸馏"
- **问题**：Agent 一次要分析多段轨迹、每段都可能很长，全 inline 进 prompt 不现实。
- **做法**（抄 auto-dream「给目录+只读工具、自己 grep 别全塞」+ Codex「先提炼摘要再回源」）：代码把相关已结束 session 落到**只读暂存目录 + manifest**；agent 用 `Read`/`Grep` **逐段导航**，每段读到够判断为止（重点扫任务/结尾成败/中途纠偏）→ **每段记一句 note**，读完即放、只攥 note；**再跨 note 找 ≥2 反复**。
- **与 B2 不矛盾**：仍覆盖每段完整 arc，只是靠 agent 逐段读+蒸馏，而非全文 inline。
- **加固漏读风险**：prompt 强制**对 manifest 每一段都产一条 note**（逼触达全部）+ 每条教训带 **≥2 段 session 引用 + 证据行**（逼真回看）。
- 用户原话："agent模式下一次要分析多个轨迹，每个轨迹都很可能很长。不适合直接喂入。适合codex和auto dream的做法。"

### B4 · success 侧 v1 不加额外限制，上线后看效果再调
初版不抬门槛、不关闭、不给更小预算，**success 与 failure 同等对待**；等上线后看实际效果再决定要不要收紧。**覆盖了我早先"判断5：success 更保守"的提议。**
- 用户原话："初版先不做太多限制，后续上线后看效果。"

### B5 · 不"定回合"：一段 prompt 让 agent 自己跑，无强制两段式
- 一手核对：Hermes 的 A（per-turn review）、Codex、auto-dream **没有一个"定回合/强制两段式"**——都是**一段 prompt，agent 在自己一个回合里自然读→想→改**。auto-dream 的"Phase 1–4"只是 prompt 里的指导小节，不是代码强制隔开的阶段。
- 所以**收回"强制两段式"**：没有"回合结构"要设计；"先想清共性再改"只是 prompt 里的一句指导。
- **Skip 不用单独决策**：prompt 写了"跨 ≥2 反复才改"，本身就意味着"没 ≥2 就不改"；只是**不照抄 Hermes 的"be active 多数 session 都该产出更新"**（与 ≥2 门槛冲突）。
- 用户原话："为啥要定回合，你看Hermes Agent的A阶段，codex prompt，auto dream有定这个吗。"

### B6 · 不设"改动数预算"，跟随 Hermes 的 be active
- 一手确认：Hermes **无每轮改动量上限**，反而催 **be active**（"a pass that does nothing is a missed learning opportunity"），Curator 甚至设**下限**（<10 archives = 停早了）。唯一的 "budget" 是 agent 这次 run 的**步数上限**（防跑飞），不是改 skill 的数量预算。
- **跟随它**：B **不设"≤K 改动"预算**；限流交给 **≥2 证据门槛 + Skip 缺省 + additive-first + 文件大小上限(<500/<300) + 快照可逆**。
- **用户点出的原因（要记牢）**：Hermes 这样设计是为了**避免 agent 为了避险干脆不改（do-nothing）**。所以我们也偏"该改就改、把 ≥2 立住的都修"，而不是人为砍到 K 条、把真·反复问题留着不修。
- **保留两个 Hermes 真有的 budget**：① 单文件大小上限（`skill_manage` 自带）；② agent run 的步数/iteration 上限（防跑飞）。
- **收回**我提的"≤K 教训预算"——那是 SkillOpt 的离线 learning-rate，不合身。
- 用户原话："Agent模式先跟随Hermes agent。他这样做的原因应该是想避免agent为避免风险直接不改。"

## B-summary · Agent 方案成形骨架（综合 A/B 各决策）

```
触发(per-skill 用 >X 次、只取已结束 session)
 → 代码: 相关 session 转录落只读暂存目录 + manifest；打开工前快照(curator_backup 式)
 → fork 一个 agent(强模型,后台)，给：一段主 prompt + skill_manage 工具 + 只读 Read/Grep + MCP 只读
 → agent 自己一个回合：逐段读轨迹蒸馏成 note → 找跨 ≥2 反复(带证据引用) → 用 skill_manage 改 → 收尾报告
 → 落 evolution_log
```
**没有**：打标器、强制阶段、效果反馈、代码 apply 流水线、改动数预算。就是"一段好 prompt + 一个会用 `skill_manage` 的 agent + 一份开工前快照"。剩 C6（触发阈值）这种小旋钮 + 主 prompt 措辞待打磨。

## D. 上线后观察点（v1 故意不在设计期定死、留给真实使用验证的）

> 这些是讨论中明确"先这样、上线看效果再调"的点。v1 不过度设计，靠观察迭代。

- **O1 · 改动量两头**：① 太少——agent 为避险**干脆不改**（do-nothing，B6 跟随 Hermes be active 正是防这个）；② 太多——一轮 B **改得过猛**。两头都观察。
  - 用户原话："至于是否改多了，也是个上线之后再观察的观察点。"
- **O2 · success 侧效果**（接 B4）：v1 不限制 success 侧，观察它是否如 Trace2Skill 实证那样**高方差/偶尔帮倒忙**，再决定要不要收紧。
- **O3 · 决策 E 的残余风险**（接 A5）：判错的坏改动若之后**不再被新证据触发**会滞留——观察"持续进化自然收敛"是否真能自愈、坏改动是否积累成问题。
- **O4 · 触发阈值 X 与"什么算一次使用"口径**（接 C6）：默认值是否合适，多少次才值得跑一轮 B。
- **O5 · ≥2 判定可靠性**：agent 在上下文里"现场聚类"找跨会话 ≥2（A 方案）是否靠谱——是否**漏读真共性**、或**凑数造假共性**。
- **O6 · MCP 部门知识注入**：可用性 + 注入质量 + 是否真减少了"成员反复手动粘资料"（spec Q12 的成功信号）。
