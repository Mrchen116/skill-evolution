## 用户场景

本系统的"用户"在 v1 只有一种：**部门成员**，平时照常用 Claude Code 写代码、做 design、跑各类任务。系统在后台默默地让 TA 手上那份 skill 越来越贴合自己的用法。整个体验是**无感的**——没有通知、没有打断、没有变慢，成员甚至不需要知道它存在。

**下发那一刻**：部门把一套打磨好的种子 skill（用 skill-creator 冷启动造出来）下发，**每个成员各拿到一份完整拷贝**。从此这份拷贝就是 TA 自己的，怎么演化只取决于 TA 自己怎么用。

**用着用着，重复的纠正消失了**：小李用 coding skill 写代码，每次都要补一句"我们用 2 空格缩进、用具名导出"。重复几次之后，他发现不用再说了——skill 自己记住了这条规范，生成的代码直接就对。设计 skill 也是：他总在某个并发边界上栽跟头、反复提醒它考虑这个 case，后来这个边界 skill 已经自带了。

**不用再从别处反复搬资料了**：以前小李做某类接口活，每次都要去内部 wiki 把那份 API 规范、那段领域术语复制粘贴进对话，才能让 Claude 按部门口径来做。现在相关 skill 已经把这部分部门知识接进来了（或带着到部门知识库里取），他问一次，系统就知道，不必再手动搬运。

**反复做的流程，自己变成了 skill**：小李每隔几天就手动走一遍"看 CI 哪挂了→定位→写一段说明"。系统注意到这是个反复出现的多步流程，悄悄沉淀成了一个 skill；之后他再碰到这类活，这个 skill 直接能用。

**新人和偶发情况不会被乱改**：刚入职、几乎还没怎么用的小王，他那份 skill 不会因为"用得太少、证据不足"就被乱动——一次性的、偶发的操作不会被误当成习惯固化进去。

**万一改坏了，不会一直坏下去**：某次自动改动让某个 skill 表现变差了，这个坏改动不会长期生效——系统会把它退回/自纠，小李不会被一个变糟的 skill 长期拖累。

**各人是各人的**：小李怎么用、他的 skill 怎么变，对小王和其他人都不可见，也不会改到别人那份拷贝。

## 验收标准

<!-- 仅用户可观察。机制名（Per-turn/Curator/批量）、编辑预算、缓冲区、fork、计数器等均为实现，归 design.md。 -->

### Requirement: 重复纠偏被 skill 吸收，成员不必反复教

#### Scenario: 同类纠正被记住
- **GIVEN** 成员在同一类任务里多次做了相同的纠正（如反复指定编码规范）
- **WHEN** 之后再做同类任务
- **THEN** 该纠正不再需要重复——skill 产出的结果已默认符合这条偏好

#### Scenario: 证据不足时不擅自改动（空态/偶发）
- **GIVEN** 某纠正只发生过一次，或成员几乎没有使用历史
- **WHEN** 系统在后台审视其使用记录
- **THEN** 不因单次/稀疏证据改动该成员的 skill，行为保持原样

### Requirement: 部门知识自动到位，成员不必反复从别处复制资料

#### Scenario: 反复手动粘贴的部门知识被纳入
- **GIVEN** 成员反复手动把某份内部规范/术语/文档粘进对话才能让任务按部门口径完成
- **WHEN** 之后再做相关任务
- **THEN** 相关 skill 已自带该部门知识或其引用，成员无需再手动搬运即可得到符合部门口径的结果

#### Scenario: 部门知识源暂不可用时降级不报错
- **GIVEN** 部门知识来源（MCP/知识库）暂时不可达
- **WHEN** 系统尝试为某 skill 补充部门知识
- **THEN** 该类知识补充被跳过，不报错、不阻塞，其它改进照常；成员日常使用不受影响

### Requirement: 反复出现的流程沉淀为可用的新 skill

#### Scenario: 重复多步流程变成 skill
- **GIVEN** 成员多次临时手动执行同一套多步流程
- **WHEN** 之后再遇到同类任务
- **THEN** 存在一个覆盖该流程的 skill 可被触发使用

#### Scenario: 一次性流程不被造成 skill
- **GIVEN** 某流程只发生过一次或明显是一次性的
- **WHEN** 系统审视使用记录
- **THEN** 不为其新建 skill（不产生用不上的冗余 skill）

### Requirement: 进化全程不打扰、不降级日常体验

#### Scenario: skill 更新对成员静默
- **WHEN** 某个 skill 在后台被改进或新建
- **THEN** 成员不收到任何通知、提示或打断，当前对话照常进行

#### Scenario: 后台运行不拖慢日常使用
- **GIVEN** 系统在后台持续运行
- **WHEN** 成员正常使用 Claude Code
- **THEN** 不出现可感知的变慢、卡顿或被阻塞

#### Scenario: 改坏的改动不长期生效
- **GIVEN** 某次自动改动导致某 skill 表现变差
- **WHEN** 成员继续使用
- **THEN** 该坏改动不会长期生效（被退回/自纠），成员不会被其长期拖累

### Requirement: 个人进化彼此隔离

#### Scenario: 一个人的进化不影响他人
- **GIVEN** 成员 A 的使用导致 A 的 skill 发生改动
- **WHEN** 成员 B 使用自己的 Claude Code
- **THEN** B 那份 skill 不受 A 影响，A 的使用记录与 skill 改动对 B 不可见

## 范围与非目标

- **在范围（v1）**：
  - 纯**个人级** skill 自动进化——基于成员自己的使用轨迹，作用于成员自己那份 skill 拷贝。
  - 两种动作：**改进现有 skill** + **从重复 workflow 新建 skill**。
  - 四类改进：补编码/规约**规范**、补**边界/失败/空态**、补全 **workflow**、经 MCP/知识库注入**部门领域知识与内部信息**。
  - 三套机制并存全上（实时快补 / 周期批量挖共性 / 维护防膨胀）。
  - 落盘**自动生效 + 可回滚**；对成员**完全静默**。
  - 冷启动：部门用 skill-creator 造种子 skill，下发时每人一份完整拷贝。
- **非目标（v1 明确不做，推迟或排除）**：
  - **部门级更新方案**：把个人改进上收回基线、把基线更新下推给全员——推迟到后续单独研究。
  - **管理员治理/审计参与**：v1 管理员不监看、不审计成员的个人进化。
  - **subagent / automation 生成**（Codex 四分法的另两类）——不在 v1。
  - **改写 Claude Code 内置 skill 或第三方插件 skill**——只读其存在以避免重复造，不改写。
  - **向成员展示更新通知 / diff / 进化看板**。
  - **独立的量化 fitness 打分门 / 在线验证集**——在线不设打分验证门，质量靠"问题反复出现即信号 + 有界可逆编辑 + 后续轨迹自纠"。
